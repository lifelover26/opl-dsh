# 并行写入与工作树

本文是 OPL DSH 处理并发写入和 Git 合并的长期约束。它描述 OPL 扩展的边界；worktree、工作目录、Forge 和 Git 的权威状态仍由各自官方 owner 持有。

## 问题

相同目录的多个写任务如果都依赖一个 OPL 进程内队列，会把正常并行变成全项目串行。这个队列不是官方 DSH 的能力合同，也不能证明任务之间发生文件冲突；它只是把并发风险换成了所有模型等待。未声明写入范围的会话更不能据此被解释为独占整个项目。

历史实现曾在 `HarnessService` 内按 cwd 和 `writeScope` 排程。来源是 OPL 提交 `b0689da` 引入的增强，不是官方 DSH 的会话锁。该默认行为已经退役。

## 写入路径

1. 用户要求并行写代码时，为每个写任务使用官方 worktree。默认工具是 `create_worktree({ name?, from? })`，服务 owner 是 `ctx.worktrees`。
2. worktree 从本地已提交基线创建新分支和独立目录，并改变调用 Session 的工作目录。未提交文件留在源 checkout。
3. 每个写任务在一个 checkout 中独立完成实现和检查。相同 cwd 的普通会话不因目录相同而互斥。
4. `writeScope` 只表达显式共享输出。只有双方都声明且路径重叠时，OPL 才等待；省略范围不建立项目所有权。
5. 写入完成且检查通过后，在 worktree 中形成可审阅提交。来自远端分支的改动通过官方 Forge 固定 `headSha` 合并；纯本地流程按仓库交付规则用 Git 合入。

## 状态负责人

| 状态或操作                  | 唯一负责人                         | OPL 的职责                                   |
| --------------------------- | ---------------------------------- | -------------------------------------------- |
| checkout、分支、Session cwd | 官方 Worktree 与 Working Directory | 调用公开服务；不复制工作树登记或 cwd 状态    |
| Git 提交、冲突与合并        | Git 与实际仓库交付流程             | 提供执行环境；不伪造锁或自动解决冲突         |
| 变更请求、检查和合并        | 官方 Forge 及其提供方              | 读取结果或发起用户明确要求的时点操作         |
| 跨 Harness 任务、交付与验收 | OPL `HarnessService`               | 保留任务关系、交付和验收；不拥有文件写入权限 |
| `writeScope` 窄互斥         | OPL `writeScope`                   | 仅协调双方都显式声明的重叠共享输出           |

## 禁止的扩展

- 禁止仅因 cwd 相同就排队、暂停或拒绝普通写任务。
- 禁止把未声明的 `writeScope` 当成整个项目的排他写锁。
- 禁止新增项目级进程内写锁、跨进程文件锁或平行 Agent 循环来替代 worktree。
- 禁止把 worktree 创建、PR 跟踪或合并结果双写到另一套 OPL 状态。
- 禁止绕过检查、验收或用户授权自动合并；合并前必须核对目标分支、`headSha` 和可合并状态。

## 验证

行为变更至少覆盖：同一 cwd 的未声明任务可并发、双方显式重叠范围仍互斥、取消等待任务不影响持有者、显式不相交范围可并发。涉及官方 worktree 或 Forge 时，再在未修改的官方桌面中验证真实调用链和状态回读。
